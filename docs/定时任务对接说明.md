# 定时任务对接说明

## 一、方案说明

- **定时器只负责调用对应的 API**，不承载具体业务逻辑。
- **真实执行在各自业务模块**：由各业务模块提供 HTTP 接口，定时任务模块在到点时对该接口发起请求，业务模块在自身路由/服务内完成逻辑。

### 执行方式：就是发一条 HTTP 请求

无论由**定时到点**触发，还是由**「立即执行」**（`POST /api/scheduler/trigger/<task_id>`）触发，执行方式都是同一种：

- 根据任务的 **type** 找到对应的**业务 API 地址**（在 `scheduler/manager.py` 的 type → API 映射中配置）。
- 向该 API 发**一条 HTTP 请求**（方法、路径、body 由 type 决定，body 一般用任务里的 `data`）。
- 业务逻辑**只在该 API 所在模块**中运行，定时任务模块不执行业务代码，只负责发请求、解析响应和打日志。

即：**执行 = 运行一个 HTTP 请求（调用业务 API）。**

这样带来的好处：

- 业务边界清晰：1688、拼多多等逻辑只在自己的 API 与 spider 里，定时模块不依赖业务实现。
- 对接简单：新业务只需提供一个可调用的 API，再在定时任务里配置「到点调哪个 API」即可。
- 可复现、可调试：同一逻辑既可由定时触发，也可由人直接调同一 API（Postman、cron、脚本等）。

## 二、对接流程（新业务接入定时任务）

### 1. 业务侧：提供可被调用的 API

在各自模块（如 `api/routes/order_1688_routes.py`）中提供 HTTP 接口，例如：

- 路径：`POST /api/order_1688/fill_detail`
- 请求体：按需（可为空 `{}`）
- 响应：建议 JSON，至少包含 `success`，以及业务需要的字段（如 `filled_count`、`message`）

业务逻辑只写在该 API 对应的路由与下层服务中，不要写在定时任务模块里。

### 2. 定时任务侧：注册「类型 → 调哪个 API」

在 **`src/scheduler/manager.py`** 的 `get_task_handlers()` 中：

- 增加一种 **task type**（如 `order_1688_fill_detail`）。
- 该 type 对应的 **handler 只做一件事**：按约定（如 `config.HOST/PORT`）拼出本服务的 base URL，然后对该业务的 API 发 HTTP 请求（如 `POST /api/order_1688/fill_detail`），并根据响应解析出 `(code, message)` 用于日志。

即：**定时器到点只调 API，不直接调业务函数。**

### 3. 配置任务：在 tasks.json 中加一条

在 **`src/scheduler/tasks.json`**（或运行后生成的同结构配置）中增加一条任务：

- `id`：唯一标识，建议与 type 或业务含义一致（如 `order_1688_fill_detail`），或使用 UUID。
- `name`：展示用名称。
- `type`：必须与 `get_task_handlers()` 中注册的 type 一致。
- `data`：请求 body，会传给该 type 的 handler；handler 内部一般会原样作为 API 的 body。
- `cron`：五段 cron（分 时 日 月 周），如 `0 * * * *` 表示每小时整点。

新增/修改 tasks 后，需重启应用或由调度器重新加载配置后才会生效。

### 4. 可选：在「定时任务」页面对接

- 前端「定时任务」列表会拉取 `GET /api/scheduler/jobs`，展示所有在 `tasks.json` 中配置的任务。
- 每条任务可「**立即执行**」：请求 `POST /api/scheduler/trigger/<task_id>`；服务端根据 task 的 type 向对应业务 API **发一条 HTTP 请求**，与定时到点时的执行方式一致。
- 新增/删除任务通过 `POST /api/scheduler/tasks`、`DELETE /api/scheduler/tasks/<task_id>` 完成，对应写入/更新 `tasks.json` 并刷新内存中的调度。

## 三、tasks.json 规范

- 路径（运行时）：由 `get_safe_data_path("scheduler")` 决定，一般为项目或用户目录下的 `scheduler/tasks.json`。
- 种子文件（规范示例）：**`src/scheduler/tasks.json`**，应用首次运行且本地尚无配置时会按此文件初始化。

单条任务结构：

```json
{
  "id": "任务唯一标识",
  "name": "任务展示名称",
  "type": "与 get_task_handlers() 中注册的 type 一致",
  "data": {},
  "cron": "0 * * * *"
}
```

**执行时配置从哪来：**

- 定时到点或「立即执行」时，调度器从 **tasks.json**（用户数据目录下的 `scheduler/tasks.json`）按 `task_id` 取出该任务，把 **`task["data"]`** 原样传给该 type 的 handler。
- 即：**你看到的「配置」就是任务里的 `data` 字段**。前端「新增任务」时填的「运行参数 data（JSON）」会存进 `task.data`，执行时 handler 收到的就是它。
- 以 `order_1688_fill_detail` 为例：handler 会读 `data.url`（不填或非法则用 `Config.HOST:Config.PORT` + 固定路径）、`data.data` 作为 POST body。因此可在任务里配置例如：`"data": { "url": "http://127.0.0.1:8887/api/order_1688/fill_detail", "data": {} }`。

- **cron**：分 时 日 月 周，空格分隔，如 `0 * * * *` 表示每小时整点。
- **data**：对象，会传给该 type 的 handler，由 handler 决定是否作为请求体传给业务 API。

## 四、现有示例：1688 订单补详情

| 项目 | 说明 |
|------|------|
| 业务 API | `POST /api/order_1688/fill_detail`（无 body 或 `{}`） |
| 业务逻辑位置 | `src/api/routes/order_1688_routes.py` → 调用 `spider.order_1688.run_detail_fill_batch` |
| 定时任务 type | `order_1688_fill_detail` |
| 定时器行为 | 到点向业务 API 发 POST：URL 优先用任务 `data.url`，未配置则用 `http://{Config.HOST}:{Config.PORT}/api/order_1688/fill_detail`，不直接执行业务代码 |
| 配置示例 | `src/scheduler/tasks.json` 中一条：`id` / `type` 为 `order_1688_fill_detail`，`cron` 如 `0 * * * *` |

对接关系小结：

1. 业务模块提供并实现 **`POST /api/order_1688/fill_detail`**。
2. 定时任务模块在 **`get_task_handlers()`** 中注册 type **`order_1688_fill_detail`**，handler 内部只发 HTTP 请求到上述 API。
3. **tasks.json** 中配置一条 type 为 `order_1688_fill_detail` 的任务，设定 cron。
4. 定时到点 → 调度器调用 handler → handler 调 API → 业务在 order_1688 模块内执行。

## 五、相关 API 一览

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/order_1688/fill_detail` | 1688 补详情（业务 API；定时/立即执行都是向此接口发 HTTP 请求） |
| GET | `/api/scheduler/jobs` | 列出所有定时任务（含下次执行时间） |
| GET | `/api/scheduler/types` | 列出已注册的 task type（用于新增任务时的类型选择） |
| POST | `/api/scheduler/tasks` | 新增一条定时任务（body: name, type, data, cron） |
| DELETE | `/api/scheduler/tasks/<task_id>` | 删除指定定时任务 |
| POST | `/api/scheduler/trigger/<task_id>` | 立即执行指定任务：**执行方式 = 向该任务 type 对应的业务 API 发一条 HTTP 请求**（与定时到点一致） |

## 六、配置项（config）

- **SCHEDULER_ENABLED**：是否启用定时任务模块（默认 True）。
- **SCHEDULER_ORDER_1688_FILL_CRON**：仅用于「种子」里 1688 任务的默认 cron，格式为五段（分 时 日 月 周）。实际运行以 **tasks.json** 中该任务的 `cron` 为准。
- 本服务地址：**HOST**、**PORT**，定时器调用本机 API 时使用（如 `http://127.0.0.1:8887`）。

## 七、小结

- **执行方式**：**就是运行一个 HTTP 请求**——向该任务 type 对应的业务 API 发请求；定时到点和「立即执行」都是这一种方式。
- **定时器**：只按 cron 触发，根据 task 的 **type** 找到对应 API，发 HTTP 请求，不执行业务代码。
- **业务方**：在各自模块提供 API，实现全部业务逻辑；定时任务不直接依赖业务实现，只依赖「可调用的 API」。
- **对接步骤**：业务提供 API → 在 scheduler 的 `get_task_handlers()` 中注册 type，handler 只做「向该 API 发 HTTP 请求」→ 在 tasks.json 中配置任务（id、name、type、data、cron）。

按此方案，后续新业务只需：**暴露 API + 注册 type（执行 = 调该 API 的 HTTP 请求）+ 配置 tasks.json**，即可接入定时任务，无需把业务逻辑放进定时模块。
